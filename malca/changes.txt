 A. events.py — Answers to Questions

 compute_symmetry_score

 - baseline_flux: Needed. The symmetry score is defined as the difference in integrated deviation from baseline on ingress
 vs egress. Without a baseline level you can't compute the deviation integrals. It's an optional override; if None it
 estimates via biweight_location.
 - t_sc / f_sc / t_ce / f_ce: Agreed, rename to e.g. t_ingress, mag_ingress, t_egress, mag_egress.
 - len(t_sc) < 2 check: Redundant. The guard on line 149 already enforces start_idx < center_idx < end_idx, so the slices
 [start_idx:center_idx+1] and [center_idx:end_idx+1] each have ≥ 2 elements by construction. Remove it.
 - Trapezoidal integration: Correct choice. Light curves are irregularly sampled. Simpson's requires equal spacing.
 Trapezoidal is the standard and appropriate method here.
 - Symmetry score vs skewness: Not the same thing. Symmetry score compares integrated ingress vs egress areas (physically
 motivated for disk-occultation profiles). Skewness is a statistical moment of the flux distribution. Both are informative
 but measure different things. Keep both.

 classify_run_morphology

 - Docstring is wrong: Says "gaussian vs paczynski vs noise" but the code also fits skew_gaussian (dips) and fred (jumps).
 Fix the docstring.
 - "freq" kernel: There is no frequency/periodic kernel in this function. If you meant to add one, it isn't here. FRED is
 present (lines 292–317). Clarify what you meant by "freq."
 - Gaussian vs skew_gaussian as separate fits: Keep them separate. BIC penalizes the extra alpha parameter in skew_gaussian.
  Fitting both and comparing BIC is the right approach—it avoids penalizing the simpler model.
 - baseline_guess = nanmedian: Correct as an initial guess for curve_fit. Using the GP baseline here would be expensive
 (computed per-run) and unnecessary—it's just a starting point for the optimizer.
 - t_seg / y_seg / e_seg: Rename to t_padded, mag_padded, err_padded.
 - len(t_seg) < 4: Can it happen? Technically yes if the LC has < 4 total points, but pre_filter should prevent that in
 production. It's a safety check for direct invocation. Keep it but it's low-priority.
 - More morphologies: Candidates to consider: flat-bottom dip (disk occultation), V-shaped dip (EB). Worth adding
 eventually.

 build_runs

 - "cur" is abstruse: Rename to current_run.
 - max_gap_days minimum of 1.0: Defensible. ASAS-SN cadence is ~1 day. A max_gap < 1 day would fragment every observation
 gap into separate runs. The 1.0 floor only applies to the auto-calculated value; explicit --run-max-gap-days overrides it
 entirely. Keep it, but note the user can override.
 - max_gap_days ever specified other than None: No. It's always None in both detect.py and events.py defaults. The
 auto-calculation (99.73th percentile of gaps) always runs.
 - **np.diff(jd) < 0**: The dt > 0 filter is a safety measure. Data should be sorted, but it isn't explicitly sorted before
 build_runs is called in bayesian_event_significance. Either sort jd before calling build_runs, or keep the filter. Sorting
 is the cleaner fix.
 - max_gap_days and allow_gap_points separately: Both are needed. max_gap_days is temporal (breaks across observing seasons
 ~180-day gaps). allow_gap_points is index-based (allows 1-2 missing observations within a run). They're orthogonal
 constraints.

 filter_runs

 - robust_median_dt_days in stats.py: stats.py is the right home. It's a pure statistical utility. events.py and utils.py
 are not better fits.
 - min_points ever < 2: Yes. build_runs can produce single-point runs (one triggered index with no neighbors within gap
 tolerance). The min_points=2 filter removes them. Needed.
 - score_vec explainer: score_vec is the per-point significance array—either log Bayes factor or event probability, one
 value per data point in the LC. filter_runs uses it to compute run_max (the peak significance within a run) and run_sum
 (total significance). These are used downstream to rank which runs are the most significant detections.

 compute_global_loglik_numba

 - log_1mp: Rename to log_1_minus_p or log_complement_p.
 - "grids" naming for Pb/Pf: log_Pb_grid shape is (M_mag_grid, N_points). The "grid" refers to the M axis (magnitude grid).
 The naming is defensible but mildly confusing since N is the point axis. Could rename to log_Pb and log_Pf (drop "grid")
 since the grid dimension is just the first axis.
 - log1p math walkthrough: The inner loop computes log(Pb[m,i]p + Pf[m,i](1-p)) for each data point i. In log-space this is
 log(exp(log_Pb + log_p) + exp(log_Pf + log_1mp)). The log-sum-exp trick: log(exp(a) + exp(b)) = max(a,b) + log(1 +
 exp(min-max)). log1p(x) = log(1+x) is numerically stable when x is small (which it is when one term dominates). This avoids
  overflow/underflow.
 - i vs n for loop variable: i is standard for point index. n typically denotes a count (N points). Using n as a loop
 variable would shadow that convention. Recommend keeping i for point index, but if you insist on consistency with m/p, use
 j instead.
 - Better function names: compute_global_loglik_numba → marginal_loglikelihood_grid. fast_loo_event_prob_numba →
 loo_event_probabilities.
 - nogil/parallel/fastmath/boundscheck: nogil is implicit with njit. boundscheck=False is the njit default. fastmath=True is
  already set. parallel=True would give speedups on compute_global_loglik_numba—the outer m loop is embarrassingly parallel.
  Requires changing range(M) to prange(M) and importing prange from numba. For fast_loo_event_prob_numba, the outer i loop
 over N points is also parallelizable. Worth doing for both.

 fast_loo_event_prob_numba

 - run_allow_gap_points scope: It's across the whole light curve (all cameras merged). build_runs operates on the merged JD
 array.
 - parallel: Yes, the outer loop over i (N points) is embarrassingly parallel. Use prange.

 run_bayesian_significance

 - Duplicated dip/jump blocks: The two calls differ only in kind, p_min/p_max, mag_grid, and logbf_threshold. You could loop
  over a config dict: for kind, cfg in configs.items(): results[kind] = bayesian_event_significance(...). Saves ~20 lines.
 Readability is fine with a well-named config dict.

 process_one

 - The import try/except block (lines 1158–1168): The first two branches are IDENTICAL (from malca.plot import
 read_skypatrol_csv). This is a bug/leftover. Should be a single top-level import. Move from malca.plot import
 read_skypatrol_csv to the module-level imports at the top.
 - -light-curves.csv: Remove. Update any glob patterns or filename expectations that look for this suffix.
 - read_skypatrol_csv tuple return check: The tuple check + ValueError is overly defensive. If read_skypatrol_csv's contract
  is to return a DataFrame, just call it and let it fail naturally if the contract is broken.
 - try/except around read_lc_dat2 / read_lc_csv: These catch generic Exception and re-raise as ValueError. They add no
 value—just let the original exception propagate. Remove the try/except wrappers.
 - n_points < 10 check: pre_filter checks time span and cadence, not raw point count. A 10-point floor is a different (and
 quick) sanity check. Keep it—it's cheap and guards against pathological files.
 - auto_filter_bad_cameras: DO NOT REMOVE. It is NOT a duplicate of post_filter's raw2 usage or pre_filter's camera_median
 filter. Three distinct things:
   - pre_filter camera_median: static check—is this camera's median outside the mag bin? (uses .raw2 medians)
   - auto_filter_bad_cameras (utils.filter_bad_cameras): dynamic check—does this camera have anomalous scatter/offset
 relative to peers in the actual LC? (uses the LC data itself + .raw2 for expected scatter)
   - post_filter raw2 usage: validation/diagnostics only, not filtering
 - sorted(...)[0] → max(...): Yes. max(run_list, key=lambda x: x['run_max']) is correct and more efficient.
 - camera# column check: Needed. SkyPatrol CSVs have different column names than .dat2 files. The check guards against
 missing camera column.
 - "Use GP baseline for scoring" comment: Misleading. The code uses res["df_base"] which is whatever baseline was configured
  (gp, trend, etc.). Fix the comment.
 - Jump scores: process_one only computes dipper_score, not jump scores. compute_event_score in score.py does support
 event_type parameter. Adding jump scoring here is straightforward—mirror the dip block for jumps. Worth doing.
 - metadata-csv 'path' column check: Appropriate. This is a user-facing input boundary—validation here is correct.
 - log() function: Should be in utils.py and imported. Or just use Python's logging module which already does this. The
 current per-module pattern leads to duplication (detect.py also defines its own log()).
 - pyarrow ImportError checks: Remove. pyarrow is required in pyproject.toml.
 - Checkpoint exception handling: The "Continuing without resume" on checkpoint-write failure IS dangerous—you'd silently
 lose resume state. These should be hard errors (raise), not warnings. Filesystem I/O failures on HPC are real but the
 correct response is to fail loudly, not silently continue.
 - "inputs" positional arg: Legacy. Remove it. The --input flag handles everything.
 - --p-points help text says "logit-spaced": The grid function used depends on trigger_mode. Help text is slightly
 misleading. Fix it.
 - sigma_eff: Enabled by default (use_sigma_eff=True). It adds GP predictive variance + sigma_floor in quadrature to the
 photometric error. This is the correct thing to do—it accounts for baseline model uncertainty.
 - "path" not in meta_df.columns check: Yes, this can reasonably occur if the user passes a wrong file. Keep it.
